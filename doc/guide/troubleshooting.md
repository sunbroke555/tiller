# 常见问题与排查

先区分是浏览器到 Tiller、Tiller 到 PVE，还是 PVE 操作本身出了问题。记录发生时间、页面、目标资源和错误信息，避免重复执行可能改变资源的操作。

## 打不开 Tiller

1. 确认进程仍在运行，查看启动日志中的监听地址。
2. 检查浏览器使用的协议和端口：配置了 TLS 时用 `https://`，未配置时是 `http://`。
3. 检查主机防火墙、反向代理与 `ALLOW_FROM` 范围。
4. 如果使用 `LISTEN=127.0.0.1:8080`，其他设备不能直接访问该端口，应通过反向代理访问。

能打开 `/healthz` 只表示 Tiller 的 HTTP 服务可达，不保证 PVE 已连通。

## 无法连接 PVE

检查 `PVE_URL` 的主机、端口和协议。若 Tiller 不运行在 PVE 主机上，默认的 `127.0.0.1` 通常不是正确地址。

浏览器只显示简化的连接错误。具体网络或证书原因写在 Tiller 服务端日志中；查看是否是证书更换、指纹不符、CA 不受信任或网络不可达。

更换证书后应核对新证书并更新对应配置，不要为了消除错误长期启用 `PVE_INSECURE_TLS=1`。

## 登录失败或提示等待

先核对用户名、认证域和密码。PAM 与 PVE 内部认证域不是同一个账号库。

连续失败会触发按客户端地址和用户名的限速，最多可能需要等待 15 分钟或 5 分钟。按页面提示等待，并在再次尝试前修正输入。如果经过反向代理，检查 `TRUSTED_PROXIES`，避免所有用户被识别成同一地址。

两步验证码失败时检查手机时间、认证器条目和验证码是否过期。恢复码只能使用一次。

## 安全密钥或 OpenID 无法使用

WebAuthn 需要安全上下文，并受域名约束。确认正在通过 HTTPS 访问，且当前地址与 PVE 的 WebAuthn 设置匹配。

OpenID 跳转失败时，检查身份提供方中允许的回调地址是否与当前 Tiller 地址对应，以及反向代理是否保留了正确的访问主机信息。

## 没有按钮或提示权限不足

按钮可用性取决于账号权限、资源状态、PVE 版本和功能前置条件。

- `401`：通常是登录失效，重新登录。
- `403`：检查目标资源的有效权限，也检查代理是否正确保留 Host，避免请求来源校验失败。
- 参数错误：按字段提示修正，必要时查看任务日志。

## 控制台打不开或反复断开

确认客户机正在运行，节点可达，账号具有控制台权限。普通 API 请求成功而控制台失败时，优先检查反向代理是否支持 WebSocket，以及连接超时设置。

更换域名、协议或证书后重新打开页面，避免继续使用旧连接。

## 配置保存后没有生效

检查页面是否标注待应用或待重启。虚拟机的部分硬件需要关闭后重新启动；节点网络、SDN 等可能需要单独执行应用。

如果操作创建了任务，先看任务最终状态，再检查配置。不要仅凭表单关闭或请求提交成功就认定变更完成。

## 更新后界面异常

先刷新页面或关闭后重新打开。若浏览器仍使用旧资源，可以清除此站点的缓存或站点数据后重试；清除站点数据会退出登录，并重置当前浏览器保存的偏好。

反向代理不要长期缓存 HTML、服务工作线程和文档页面。文档地址应为当前实例的 `/docs/`，直接打开章节链接也应正常显示。

## 文档没有随程序出现

使用仓库的 `make server` 重新构建，确保文档与管理界面一起打包。如果设置了 `WEB_DIR`，该目录也需要包含构建后的 `docs/` 子目录。

## 提供排查信息

提供 Tiller 构建来源、PVE 版本、浏览器、发生时间、复现步骤和必要日志。截图或日志中不要包含密码、Cookie、令牌、恢复码和私钥。
